# Spec - Оформлення оренди в «Споряджай»

Побудуй модель взаємодії для UC-02 «Оформити оренду». Джерела - [ER-модель](../lab-1/model.mmd), [правила доступності](../lab-2/spec.md#зайнятість-і-дати) та [Gherkin завдання 2](../lab-2/requirements.md#3-сценарії-gherkin).

Учасники - Customer, форма оренди, RentalService (UC-02), AvailabilityService (UC-03) і сховище. Customer уже обрав пункт, предмети й дати. У межах роботи - підтвердження броні та відмови під час оформлення.

## Сценарії

| Gherkin | Кроки й очікуваний результат |
| --- | --- |
| 2 | Перевірити SLP-01, створити Rental `reserved` у пункті «Поділ», записати ціну 80.00 в RentalLine. |
| 3 | Знайти відкриту позицію TENT-01 в `active` після `due_at`. Відхилити оренду. |
| 4 | Перевірити стан TENT-02. Відхилити оренду для `maintenance`. |
| 9 | Порівняти грудневу бронь TENT-01 із жовтневим запитом. Зберегти жовтневі дати в новій броні. |
| 10 | Перевірити порядок дат. Для `due_at <= starts_at` повернути відмову. |
| 12 | Перевірити зайнятий TENT-01 і вільний SLP-01. Відхилити весь запит. |

## Критерії прийняття

- **C1.** Для кожного рядка створи окремий блок `sequenceDiagram` у `model.md`. Покажи кроки Gherkin та результат.
- **C2.** Використай реалістичні виклики, пунктирні відповіді, activation bars і хоча б один `alt`, `opt` або `loop` на сценарій. Спільні активації відкривай до фрагмента й закривай після нього.
- **C3.** UC-03 перевіряє інтервал, стан і відкриті позиції. За успіху збережи `Rental` та всі `RentalLine` із копією `EquipmentType.daily_rate`. За відмови нових записів немає. Використовуй сутності та атрибути з ER-моделі.

## Нефункціональні вимоги

- **NFR-01. Узгодженість.** Одночасні запити на один предмет на ті самі дати дають одну бронь.
- **NFR-02. Атомарність.** Збій під час запису позицій залишає 0 нових записів цієї спроби.
- **NFR-03. Конфіденційність.** Відмова не розкриває дані іншого клієнта.
- **NFR-04. Час відповіді.** Ціль для реалізації - p95 до 500 мс на сервері за 10 одночасних клієнтів.
